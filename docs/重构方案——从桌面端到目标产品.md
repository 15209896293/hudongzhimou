## 二、重构策略总纲

### 2.1 核心原则

1. **保留资产，渐进演进**：当前桌面端的规则引擎、运动配置JSON、安全阈值体系是核心资产，应在重构中保留并复用
2. **双轨并行，风险隔离**：桌面端持续维护（比赛演示用），移动端全新开发（未来产品化用）
3. **先做MVP，再补全功能**：优先实现计划书中"可演示"的核心能力，再逐步叠加IMU、非遗等增值功能
4. **后端先行，多端复用**：云端服务（大模型中转、用户数据、动作包管理）一旦建成，可同时服务桌面端和移动端

### 2.2 演进路线图（三阶段）

```
当前桌面端 ──→ 混合过渡期 ──→ 云端增强版 ──→ 目标移动端
  (Phase 0)     (Phase 1)       (Phase 2)       (Phase 3)
```

| 阶段 | 时间 | 核心目标 | 交付物 |
|------|------|----------|--------|
| **Phase 0** | 0-2周 | 桌面端能力补全 | 可作为比赛Demo的稳定版本 |
| **Phase 1** | 2-6周 | 桌面端+云端联调 | 接入大模型API，验证语义分析能力 |
| **Phase 2** | 6-12周 | 后端服务化 | 建成可复用的云端服务层 |
| **Phase 3** | 12-20周 | 移动端开发 | Flutter App上线 |

## 三、Phase 0：桌面端能力补全（当前→2周内）

### 3.1 目标
在不改动架构的前提下，将当前桌面端产品打磨到可稳定演示、功能闭环的状态。

### 3.2 待补全能力清单

| 优先级 | 能力项 | 说明 | 工作量 |
|--------|--------|------|--------|
| P0 | **用户档案系统** | 新增"用户管理"面板，支持身高/体重/年龄/损伤史录入，存入JSON本地文件 | 2-3天 |
| P0 | **个性化阈值生效** | 将已有的`personal_thresholds`字段真正接入规则引擎，根据用户损伤史动态调整阈值 | 1-2天 |
| P0 | **关节趋势报告增强** | 将现有基础统计升级为"7天关节健康趋势"可视化报告（角度曲线+异常频率） | 2-3天 |
| P1 | **训练记录详情页** | 点击历史记录条目，展示该次训练的完整关节角度变化曲线 | 2天 |
| P1 | **导出功能** | 支持将训练记录导出为PDF/图片，方便用户分享或提交给老师 | 1-2天 |
| P2 | **多用户切换** | 支持在同一台电脑上切换不同用户档案（适合实训中心场景） | 2-3天 |

### 3.3 技术方案要点

- **用户档案存储**：复用现有`data/`目录结构，新增`user_profiles.json`，字段对齐计划书中的"损伤史"设计
- **个性化阈值接入**：修改`angle_safety_detector.py`，在`evaluate_safety()`前增加`apply_personal_adjustment()`步骤，根据用户档案中的损伤史调整阈值
- **趋势报告**：复用现有`workout_history.json`数据，使用`matplotlib`或`PyQtGraph`绘制折线图，嵌入到统计面板中

### 3.4 验收标准
- [ ] 新用户首次打开App，弹出档案录入引导
- [ ] 有膝关节损伤史的用户做深蹲，安全阈值自动收紧（如正常下限90°→该用户100°）
- [ ] 统计面板可查看"本周膝关节稳定度趋势"折线图
- [ ] 单用户全流程（录入→训练→查看报告→导出）可在5分钟内完成

## 四、Phase 1：桌面端+云端联调（2-6周）

### 4.1 目标
为当前桌面端接入云端大模型API，验证"语义级运动风险分析"的技术可行性，同时搭建后端服务雏形。

### 4.2 架构调整

```
当前桌面端 ──HTTP──→ 轻量后端服务 ──HTTPS──→ 大模型API（通义千问/DeepSeek）
   │                        │
   └── 本地RTMPose          └── 用户数据缓存（Redis/内存）
        规则引擎             运动配置同步
```

### 4.3 后端服务设计（最小可行版）

**服务一：大模型分析中转（`/api/analyze`）**
- 入参：动作名称 + 15帧骨架坐标数组 + 用户损伤史文本
- 出参：风险等级（safe/warning/danger）+ 纠错建议文本 + 安全评分（0-100）
- 技术栈：Python FastAPI（团队技术栈一致，学习成本低）
- 部署：轻量云服务器（2核2G）或本地笔记本临时暴露公网（ngrok）

**服务二：用户档案云端备份（`/api/profile`）**
- 入参/出参：用户ID + 身高/体重/损伤史JSON
- 存储：云MySQL或轻量数据库（SQLite放服务器上）
- 目的：验证"多设备数据同步"流程，为移动端做准备

### 4.4 桌面端改造点（仅增不改）

| 改造项 | 方案 |
|--------|------|
| 新增"AI分析模式"开关 | 控制面板增加切换按钮：本地规则引擎 / 云端大模型 |
| 新增网络请求模块 | 使用`requests`库，封装`BackendClient`类，处理超时/重试/离线降级 |
| 骨架数据打包 | 每15帧收集一次骨架坐标（复用现有`current_keypoints`），组装JSON |
| 离线降级策略 | 网络异常或无后端时，自动切回本地规则引擎，用户无感知 |
| 大模型结果展示 | 在视频画面上叠加"AI建议"文字气泡（区别于本地规则的固定提示） |

### 4.5 提示词工程（Prompt Design）

向大模型发送的提示词应包含以下结构化信息：

```
你是一位运动康复专家。请根据以下信息分析用户的动作风险：

【动作名称】：深蹲
【用户身体信息】：身高175cm，体重70kg，年龄22岁
【用户损伤史】：左膝半月板术后6个月
【15帧骨架坐标】（单位：像素）：
  Frame 1: [{"x":320,"y":240,"z":0.5,"v":0.95}, ...]
  ...

请输出JSON格式：
{
  "risk_level": "warning", // safe / warning / danger
  "suggestion": "左膝内扣明显，请向外打开膝盖，避免半月板二次损伤",
  "score": 78, // 0-100，越高越安全
  "affected_joints": ["left_knee"] // 涉及关节列表
}
```

### 4.6 验收标准
- [ ] 桌面端开启"AI分析模式"后，每5秒收到一次大模型返回的语义级建议
- [ ] 同一动作，有/无损伤史的用户，大模型返回不同的安全评分
- [ ] 断网时自动降级到本地规则，恢复网络后自动切回大模型
- [ ] 后端服务可支持10个并发请求（满足比赛演示需求）

## 六、Phase 3：移动端开发（12-20周）

### 6.1 目标
基于Phase 2建成的后端服务层，开发Flutter移动端App，实现计划书中的完整产品形态。

### 6.2 技术选型确认

| 层面 | 选型 | 理由 |
|------|------|------|
| 跨端框架 | Flutter 3.x | 一套代码同时编译iOS/Android，UI一致性好 |
| 姿态检测 | MediaPipe PoseLandmarker | Google官方Flutter插件，端侧推理无网络依赖，33关键点 |
| 大模型 | 通义千问/DeepSeek API | 中文运动语义理解优秀，有免费额度 |
| 后端 | FastAPI (Python) | 团队已有Python基础，迁移成本低 |
| 数据库 | MySQL + Redis | MySQL存结构化数据，Redis缓存热点 |
| 存储 | 腾讯云COS / 阿里云OSS | 国内访问速度快，与云服务器同厂商有套餐优惠 |
| 认证 | Firebase Auth / 微信SDK | 支持手机号+微信两种登录方式 |

### 6.3 关键算法移植（桌面端→移动端）

**3D真实骨架换算算法**
- 桌面端已有"骨架比例计算"雏形（基于身高推算骨骼长度）
- 移动端需将其实现为Dart代码，核心公式不变：
  - `缩放系数 = 躯干理论长度(mm) / 肩-髋像素距离`
  - `真实坐标 = 归一化坐标 × 缩放系数`
- 深度坐标：利用MediaPipe的`z`值 + 摄像头焦距参数换算

**负荷计算**
- 桌面端已有"膝关节受力力矩"计算逻辑
- 移动端复用公式：`力矩 = 体重(kg) × 水平距离(m)`
- 增加更多关节的负荷计算（腰椎、肩关节）

**个性化阈值系统**
- 桌面端的`personal_thresholds` JSON结构可直接复用
- 移动端从后端拉取用户档案后，在本地应用阈值调整

### 6.4 IMU贴片双模式（远期规划）

IMU贴片涉及硬件设计，建议作为**第二阶段产品**开发：
- **Phase 3.1**（12-16周）：纯视觉模式App上线
- **Phase 3.2**（16-20周）：启动IMU硬件原型设计（委托硬件团队或院校合作）
- **Phase 3.3**（20周后）：视觉+IMU融合算法验证

IMU贴片技术路线建议：
- 传感器：MPU-6050/MPU-9250（6轴/9轴，低成本）
- 通信：蓝牙BLE（低功耗，与手机直连）
- 贴放位置：膝关节、腰椎（初期两个点位）
- 融合算法：视觉提供全局姿态，IMU提供高频关节角速度，卡尔曼滤波融合

### 6.5 验收标准
- [ ] iOS/Android双端核心功能一致
- [ ] 摄像头实时骨架识别帧率≥15fps
- [ ] 大模型分析响应时间<3秒
- [ ] 训练记录7天自动清理，云端长期备份
- [ ] 通过TestFlight/应用商店审核

## 十、对比赛答辩的建议

### 10.1 演示策略
- **优先演示桌面端（Phase 0完成后）**：桌面端功能完整、运行稳定，适合现场演示
- **移动端展示原型图或TestFlight版本**：如果Phase 3进展快，可展示真机；否则用Figma/设计稿说明
- **重点突出"差异化"**：现场做对比演示——同一个错误动作，Keep只计数，护动智眸会报警并告知风险原因

### 10.2 回答"技术可行性"的标准话术
> "当前展示的是桌面端原型，核心算法（骨架识别+安全规则引擎）已经跑通。移动端方案采用Flutter+MediaPipe，与当前桌面端的RTMPose在底层原理上相通（都是人体关键点检测），团队已验证MediaPipe的Flutter插件可用性。IMU贴片作为第二阶段的硬件创新，目前处于方案设计阶段，已与XX院校电子工程系建立合作意向。"

### 10.3 回答"与竞品的区别"的标准话术
> "Keep等产品的核心KPI是用户活跃度和付费转化，因此产品设计必须提供正向激励（打卡、奖章）。而防伤预警本质是负向反馈——告诉用户'你做错了'——这会降低留存率，与商业逻辑冲突。我们选择了B端先行策略，学校怕学生受伤、健身房怕客诉，他们愿意为'安全'买单，这是我们与所有C端健身App的本质差异。"
