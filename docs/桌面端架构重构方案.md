# 护动智眸桌面端架构重构方案
## 纯方案文档，不涉及代码改动

---

## 一、当前架构问题诊断

### 1.1 核心架构问题

#### 问题1：主窗口（main_window.py）是"超级枢纽"

`WorkoutTrackerApp`（474行）承担了太多职责：

| 职责 | 代码位置 | 问题 |
|------|----------|------|
| 设备检测（GPU/CUDA） | `_detect_device()` 第84-125行 | 包含底层硬件探测逻辑，应在初始化阶段独立完成 |
| 模型初始化 | `_init_core_components()` | 直接创建 RTMPoseProcessor，耦合了AI层 |
| 帧处理与安全检测调度 | `update_image()` 第322-368行 | **最关键的问题**——帧忙锁、安全节流、语音触发全部堆在主窗口 |
| 状态变量存储 | `_init_state_variables()` | 12个状态变量散落在主窗口上 |
| 所有Manager的中转调用 | 20+个`def change_xxx(self)`方法 | 每个都是一行转发，纯粹的中转层 |

**本质问题**：`main_window.py` 是所有Manager的"中转站" + 帧处理调度器 + 状态仓库三重角色混合。

#### 问题2：VideoProcessor 职责混乱

`video_processor.py`（458行）同时负责：

- **UI绘制**：骨架绘制（`draw_skeleton_on_frame`）、角度线绘制（`draw_angle_lines`）、角度文字渲染
- **推理调度**：跳帧逻辑（`_inference_frame_counter`）、调用`pose_processor.process_frame()`
- **UI状态更新**：计数器显示、阶段显示、里程碑音效
- **设备/模型切换**：停止线程→重建线程→重启，包含复杂的错误回滚

一个类同时操作 OpenCV 图像 + PyQt5 UI控件 + 管理视频线程生命周期，违反单一职责。

#### 问题3：Manager模式是"假解耦"

当前5个Manager（mode/counter/stats/menu/video_processor）的实现方式：

```python
class CounterManager:
    def __init__(self, main_window):
        self.main_window = main_window  # ← 每个Manager都持有main_window引用

    def change_exercise(self, exercise_type):
        self.main_window.exercise_type = exercise_type  # ← 直接修改main_window属性
        self.main_window.exercise_counter.reset_counter()  # ← 直接操作main_window的其他组件
```

**问题**：Manager不是独立的，它们通过 `self.main_window` 直接互相访问对方的内部状态。这不是解耦，而是把代码分散到多个文件里，依赖关系反而更隐蔽。

#### 问题4：数据流经过的层次过多

一帧视频从采集到显示，经过的调用链：

```
VideoThread(QThread)
  → emit change_pixmap_signal
    → main_window.update_image()          # 帧忙锁 + 安全节流
      → video_processor.update_image()     # 推理跳帧 + 骨架绘制 + UI更新
        → pose_processor.process_frame()   # ONNX推理 + 计数
          → exercise_counter.count_xxx()   # 角度计算 + 阶段判定
```

4层嵌套，每层都有独立的跳帧/节流逻辑，难以统一管理。

#### 问题5：缺乏公共服务层

以下功能在多处重复实现：

| 功能 | 出现位置 |
|------|----------|
| exercises.json 路径获取 | `rtmpose_processor.py`、`angle_safety_detector.py`、`control_panel.py` |
| 打包环境路径判断（`sys.frozen`） | `rtmpose_processor.py`（模型路径）、`rtmpose_processor.py`（数据路径）、`workout_tracker.py` |
| 角度计算（三点夹角） | `exercise_counters.py`、`angle_safety_detector.py` 各自独立实现 |
| 状态栏消息更新 | `counter_manager.py`、`video_processor.py`、`stats_manager.py`、`mode_manager.py` 都在直接写 `statusBar.showMessage()` |

## 二、重构后的目标架构

### 2.1 设计原则

1. **主窗口只做布局和信号连接**——不持有任何业务状态，不参与帧处理逻辑
2. **引入 AppState 集中管理状态**——所有运行时状态集中到一个数据类，Manager 通过 AppState 通信，而非直接互相访问
3. **Pipeline 模式处理视频帧**——将帧处理拆为独立的流水线阶段，每阶段职责单一
4. **公共服务层抽取**——路径管理、角度计算、日志等公共能力抽取为独立模块
5. **Manager 真正解耦**——Manager 只依赖 AppState 和公共服务，不持有 main_window 引用

## 三、重构方案详解

### 3.1 新增模块：AppState（集中状态管理）

**解决的问题**：当前12个状态变量散落在 `main_window.py` 上，Manager 通过 `self.main_window.xxx` 随意读写。

**设计方案**：

```
AppState 数据类，包含所有运行时状态：

┌─ 推理相关
│     device: str               # 'cpu' / 'cuda'
│     model_mode: str           # 'lightweight' / 'balanced' / 'performance'
│     exercise_type: str        # 当前运动类型
│     show_skeleton: bool      # 是否显示骨架
│     mirror_mode: bool        # 是否镜像
│
├─ 计数相关
│     current_count: int        # 当前计数
│     manual_count: int         # 手动调整次数
│     is_resetting: bool        # 是否正在重置
│
├─ 帧数据
│     current_keypoints: ndarray  # 当前骨架关键点
│     current_fps: int           # 当前帧率
│     current_angle: float       # 当前关节角度
│
├─ 训练相关
│     start_time: float         # 训练开始时间戳
│
└─ UI状态
      current_mode: str         # 'workout' / 'stats'
      model_initialized: bool   # 模型是否已加载
```

**Manager 交互方式变化**：

```
# 当前方式（耦合）
class CounterManager:
    def __init__(self, main_window):
        self.main_window = main_window
    def change_exercise(self, type):
        self.main_window.exercise_type = type       # 直接写
        self.main_window.safety_detector.set_exercise(type)  # 跨模块访问

# 重构后方式（解耦）
class CounterManager:
    def __init__(self, app_state, safety_detector):
        self.state = app_state
        self.safety_detector = safety_detector
    def change_exercise(self, type):
        self.state.exercise_type = type              # 写状态
        self.safety_detector.set_exercise(type)       # 直接调用，不经过main_window
```

### 3.2 新增模块：FramePipeline（帧处理流水线）

**解决的问题**：当前帧处理逻辑分散在 `main_window.update_image()` 和 `video_processor.update_image()` 两处，包含帧忙锁、推理跳帧、安全节流三套独立的控制逻辑。

**设计方案**：将帧处理拆为4个独立阶段，串行执行：

```
VideoThread 发出帧信号
      │
      ▼
┌─ FramePipeline.process_frame(frame) ──────────────────┐
│                                                          │
│  Stage 1: InferenceStage                                 │
│    输入：原始帧                                           │
│    职责：调用 RTMPoseProcessor.process_frame()             │
│    输出：keypoints, angle, angle_point                    │
│    控制：跳帧逻辑（每N帧推理一次）                          │
│                                                          │
│  Stage 2: CounterStage                                   │
│    输入：keypoints, angle                                 │
│    职责：更新 ExerciseCounter 的内部状态                    │
│    输出：count, stage (up/down)                          │
│    控制：无（每帧都更新计数器状态）                         │
│                                                          │
│  Stage 3: SafetyStage                                    │
│    输入：keypoints                                        │
│    职责：调用 AngleSafetyDetector.check_safety()           │
│    输出：safety_result (level, messages, voice_tips)      │
│    控制：节流逻辑（每M帧检测一次）                          │
│                                                          │
│  Stage 4: RenderStage                                    │
│    输入：原始帧 + keypoints + angle + safety_result        │
│    职责：骨架绘制 + 角度线绘制 + 安全状态叠加 + 镜像 + 格式转换│
│    输出：渲染后的 RGB 帧（可直接给 VideoDisplay）           │
│    控制：无（每帧都渲染，保证显示流畅）                      │
│                                                          │
└──────────────────────────────────────────────────────────┘
      │
      ▼
VideoDisplay.update_image(rendered_frame)
```

**关键设计决策**：

| 决策点 | 方案 | 理由 |
|--------|------|------|
| Pipeline是类还是函数 | 独立类 `FramePipeline` | 需要持有跳帧计数器、节流计数器等状态 |
| 各Stage是方法还是独立类 | 初期用方法，后期可拆为独立类 | 当前4个阶段逻辑不复杂，拆类过度设计 |
| 跳帧/节流放在哪 | 在 Pipeline 内部统一管理 | 替代当前分散在 main_window 和 video_processor 的两套逻辑 |
| 骨架绘制代码搬到哪里 | 从 `video_processor.py` 搬到 `RenderStage` | 绘制是纯UI逻辑，属于渲染阶段 |

### 3.3 新增模块：AppController（UI→业务桥梁）

**解决的问题**：当前 `main_window.py` 有20+个 `def change_xxx()` 方法，每个都是纯转发，同时 `connect_signals()` 把所有信号手动连接。

**设计方案**：

```
AppController 职责：

1. 接收所有 UI 信号（exercise_changed, counter_reset, camera_changed...）
2. 调用对应的业务逻辑（通过 AppState + 各Manager）
3. 发射结果信号给 UI 更新

UI信号 → AppController → 业务逻辑
                          ↓
                    AppController发出信号 → UI更新

UI不再直接调用业务方法，也不再直接读取业务状态。
```

**main_window.py 的变化**：

```
重构前（474行）：
  - 设备检测逻辑
  - 12个状态变量
  - 20+个转发方法
  - 帧处理调度（帧忙锁+安全节流）
  - UI布局
  - 信号连接

重构后（预计150-200行）：
  - UI布局（setup_ui）
  - 信号连接（1行：所有UI信号连接到AppController）
  - 生命周期管理（closeEvent）
  - 仅此而已
```

### 3.4 新增模块：core/services/（公共服务层）

**解决的问题**：路径获取、角度计算、打包判断等在多处重复。


| 当前散落位置 | 统一后调用方式 |

| `rtmpose_processor.py` 第86-98行（模型路径） | `PathManager.get_models_dir()` |
| `rtmpose_processor.py` 第178-195行（数据路径） | `PathManager.get_data_dir()` |

## 四、重构前后对比

### 4.1 核心指标对比

| 维度 | 重构前 | 重构后 |
|------|--------|--------|
| main_window.py 行数 | 474行 | ~150行 |
| video_processor.py 行数 | 458行 | ~180行（仅设备/模型切换） |
| main_window 持有的状态变量 | 12个 | 0个（全部移入 AppState） |
| main_window 持有的业务方法 | 20+个 | 0个（全部移入 AppController） |
| 帧处理逻辑所在文件 | 2个（main_window + video_processor） | 1个（frame_pipeline） |
| 角度计算重复实现 | 2处 | 1处（angle_utils） |
| 路径获取重复实现 | 4处 | 1处（path_manager） |
| Manager 依赖 main_window | 全部5个 | 0个（依赖 AppState） |

### 4.2 数据流对比

**重构前**：
```
VideoThread → main_window.update_image() → video_processor.update_image()
                                                ├── pose_processor.process_frame()
                                                ├── draw_skeleton()
                                                ├── draw_angle_lines()
                                                ├── update_ui_components()
                                                └── (安全检测在main_window里做，和绘制分离)
```

**重构后**：
```
VideoThread → AppController → FramePipeline.process_frame()
                                  ├── Stage1: Inference (pose_processor)
                                  ├── Stage2: Counter (exercise_counter)
                                  ├── Stage3: Safety (safety_detector)
                                  └── Stage4: Render (骨架+角度+安全叠加)
                                        │
                                        ▼
                                  VideoDisplay.update_frame()
```

### 4.3 Manager 依赖关系对比

**重构前**：
```
main_window ← CounterManager ← (访问 main_window.exercise_counter)
main_window ← StatsManager   ← (访问 main_window.workout_tracker)
main_window ← ModeManager    ← (访问 main_window.video_thread, video_display, control_panel)
main_window ← VideoProcessor ← (访问 main_window.pose_processor, video_thread, mirror_mode...)
main_window ← MenuManager    ← (访问 main_window.pose_processor, video_thread...)
```
所有箭头都指向 main_window → 它是隐式的全局变量。

**重构后**：
```
AppState ← CounterManager (读写计数状态)
AppState ← StatsManager   (读写统计状态)
AppState ← ModeManager    (读写模式状态)

AppController → CounterManager (调用方法)
AppController → StatsManager   (调用方法)
AppController → ModeManager    (调用方法)

FramePipeline → pose_processor (推理)
FramePipeline → safety_detector (安全检测)
FramePipeline → AppState (读写帧数据)
```
每个模块的依赖关系清晰、单向、可预测。

## 五、重构执行顺序

重构按风险从低到高分5步执行，每步完成后可独立运行验证：

### Step 1：抽取公共服务层（风险：极低）

**改动范围**：新增 `core/services/` 目录，3个新文件
**不影响**：任何现有文件

1. 创建 `core/services/path_manager.py`，封装所有路径获取逻辑
2. 创建 `core/services/angle_utils.py`，封装角度计算函数
3. 创建 `core/services/config.py`，封装全局配置常量

### Step 2：引入 AppState（风险：低）

**改动范围**：新增 `app/app_state.py`，修改现有Manager
**不影响**：main_window 的运行逻辑

1. 创建 AppState 数据类，包含所有状态字段
2. 逐个修改 Manager（CounterManager → StatsManager → ModeManager → VideoProcessor），将 `self.main_window.xxx` 替换为 `self.state.xxx`
3. 在 main_window.__init__ 中创建 AppState 实例并传给各 Manager

### Step 3：抽取 FramePipeline（风险：中）

**改动范围**：新增 `app/frame_pipeline.py`，修改 `main_window.update_image()` 和 `video_processor.py`
**这是核心改动**——帧处理逻辑迁移

1. 创建 FramePipeline，4个阶段方法
2. 将 `video_processor.update_image()` 中的推理调度逻辑移入 InferenceStage
3. 将 `video_processor.draw_skeleton_on_frame()` 移入 RenderStage
4. 将 `main_window.update_image()` 中的安全检测逻辑移入 SafetyStage
5. 将 `main_window.update_image()` 的调用改为走 Pipeline

### Step 4：抽取 AppController（风险：中）

**改动范围**：新增 `app/app_controller.py`，精简 main_window
**将所有业务方法从 main_window 移入 AppController**

1. 创建 AppController，接收 UI 信号
2. 将 main_window 的 20+ 个 `def change_xxx()` 移入 AppController
3. main_window.connect_signals() 改为连接到 AppController
4. AppController 的结果通过信号返回给 main_window 更新UI

### Step 5：精简与清理（风险：低）

1. 删除 video_processor.py 中已迁移的代码
2. 删除 main_window.py 中已迁移的状态变量和方法
3. 统一所有模块使用 path_manager 和 angle_utils
4. 删除 angle_safety_detector.py 中的重复 calculate_angle
